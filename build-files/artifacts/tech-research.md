# Technical Research Artifact

## Purpose & Overview

The Technical Research artifact serves as the comprehensive research and solution analysis document that informs implementation planning. Generated by the solution-architect, this document captures technology evaluation, solution options analysis, integration patterns, and architectural guidance without prescribing specific implementation tasks.

### Key Objectives
- **Technology Research**: Evaluate and compare solution options (open-source, commercial, custom)
- **Solution Analysis**: Document integration patterns, architectural approaches, and design decisions
- **Production Readiness**: Define quality framework, security considerations, and operational requirements
- **Knowledge Base**: Serve as reference document for implementation decisions and future iterations

### Integration Points
- **Input from**: User stories, MVP requirements, market research
- **Created by**: solution-architect agent
- **References**: User story acceptance criteria, technical specifications
- **Feeds into**: Implementation plan (task-based execution guide)

### Relationship to Implementation Plan
This technical research document is a **reference companion** to the implementation plan:
- **Tech Research (this document)**: The "WHAT and WHY" - research findings, solution options, architectural guidance
- **Implementation Plan**: The "HOW" - sequential tasks, file-specific instructions, execution checklist

## Compliance Rules

### Required Fields
- **Metadata**: All fields with full timestamps (YYYY-MM-DD HH:mm:ss)
- **Core Sections**: Strategic context, research, architecture, quality framework, handoff package
- **Questions**: Minimum 3 story-scoped questions
- **Changelog**: All changes tracked with timestamps
- **API Research** (CRITICAL): If user story involves external APIs/data sources:
  - [ ] API endpoint specifications documented (URL, method, payload)
  - [ ] Sample scripts provided (curl or Python)
  - [ ] Actual JSON response structure documented (from executed script)
  - [ ] Field extraction mapping specified (API field → domain model field)
  - [ ] Validation criteria checklist completed

### Quality Standards
- **Strategic Focus**: Architecture and research without step-by-step code instructions
- **Evidence-Based**: Research-backed recommendations with sources
- **Production-Ready**: All production considerations addressed
- **Configuration**: Environment variables in `.env.local`
- **Template Adherence**: All sections present, consistent cross-references
- **API Research Depth** (CRITICAL): When user story involves external APIs:
  - **BLOCKING FAILURE**: If external API referenced but no "API Research" section → Incomplete research
  - **BLOCKING FAILURE**: If "API Research" section exists but no sample script → Cannot verify API works
  - **BLOCKING FAILURE**: If sample script provided but no actual response example → Cannot extract fields
  - **BLOCKING FAILURE**: If response example provided but no field mapping → Implementation will be ambiguous
  - **ENFORCEMENT**: solution-architect MUST execute sample scripts and capture real responses before finalizing tech research
